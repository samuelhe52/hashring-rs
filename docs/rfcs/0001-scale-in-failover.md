# 缩容与故障接管：副本放置即接管计划

本文详细说明 hashring-rs 在节点计划内退出（缩容）和节点故障时如何交接数据的所有权。它是“总体方案设计”一章的补充材料，配套的交互演示见 [0001-scale-in-failover.html](0001-scale-in-failover.html)，设计契约见 [RFC 0001](0001-ha-for-consistent-hash-cache.md)。

**一句话概括：** 一个区间的第一个 follower，恰好是 owner 离开后环会自然选出的新 owner。所以节点离开时，它的区间直接并入下一个 owner 的管辖范围，而这个 owner 早已作为 follower 持有这部分数据。接管不需要选举，关键路径上也不需要搬运大量数据。

## 1. 背景：副本如何放置

### 1.1 环、token 与区间

系统使用一致性哈希环。每个物理节点在环上占据多个 token（虚拟节点）。一个 token 负责它与前一个 token 之间的左开右闭区间 `(前一个 token, 本 token]`。键哈希到环上某点后，沿顺时针方向遇到的第一个 token 所属的节点就是它的 owner。

区间没有永久编号，完全由当前拓扑中相邻 token 的位置决定：新节点加入会插入 token，把区间切开；节点离开会删除 token，让相邻区间合并。

### 1.2 副本列表的推导规则

复制因子为 RF 时，一个区间的副本列表按下面的规则确定：

1. 从区间末端的 token 出发，它所属的节点是 **owner**；
2. 继续顺时针前进，遇到的 token 如果属于一个**尚未出现在列表中**的物理节点，就把该节点加入列表；
3. 属于已在列表中的节点的 token 直接跳过（同一台机器存两份没有容错意义）；
4. 直到列表有 RF 个节点，或所有节点都已加入。

列表中 owner 之后的节点依次称为第一个 follower（first successor）、第二个 follower……

副本位置完全由环推导出来，系统中**没有**任何单独维护的“区间 → 副本”映射表，也不允许人工指定。每个客户端、节点和 Coordinator 拿到同一份拓扑后，算出的副本列表一定相同。

### 1.3 一个例子

设环上一小段 token 依次为（数字表示 token 位置）：

```
… P(10) → A(20) → A(25) → B(40) → C(60) → D(80) → …
```

RF=3 时：

| 区间 | owner | 第一个 follower | 第二个 follower | 说明 |
| --- | --- | --- | --- | --- |
| `(10, 20]` | A | B | C | A(25) 属于 A，跳过 |
| `(20, 25]` | A | B | C | |
| `(25, 40]` | B | C | D | |
| `(40, 60]` | C | D | … | |

## 2. 核心观察：第一个 follower 就是下一任 owner

现在把 A 从环上移除。A 的两个 token 20 和 25 消失，`(10, 20]`、`(20, 25]`、`(25, 40]` 三个区间合并为 `(10, 40]`。按同样的规则重新推导：

| 区间 | owner | 第一个 follower | 第二个 follower |
| --- | --- | --- | --- |
| `(10, 40]` | B | C | D |

新 owner 是 B，而 B 原本正是 A 那两个区间的第一个 follower。这不是例子里的巧合，而是规则的必然结果：

- 移除 A 之前，A 的区间的第一个 follower，就是“从区间末端顺时针走，跳过所有 A 的 token 后，遇到的第一个节点”；
- 移除 A 之后，这个区间里的键的 owner，就是“从键的位置顺时针走，遇到的第一个 token 的节点”。A 的 token 已经不存在了，所以这正是同一个节点。

两句话描述的是同一次“跳过 A 往前走”，结果必然相同。代码中的单元测试 `first_successor_becomes_owner_when_the_owner_is_removed` 对每个区间都验证了这一点。

更一般地，**移除一个节点，对任何副本列表的影响都是：把该节点从列表中删掉，后面的节点依次前移一位，再在末尾补上顺时针的下一个节点。** 以上面的例子来看：

| 受影响的区间 | 移除 A 前 | 移除 A 后 | 需要补数据的节点 |
| --- | --- | --- | --- |
| A 的区间（并入 `(10, 40]`） | **A**, B, C | B, C, D | D（只缺原属 A 的部分） |
| B 的区间（并入 `(10, 40]`） | B, C, D | B, C, D | 无 |
| P 的区间 `(…, 10]` | P, **A**, B | P, B, C | C（新补到末尾的节点） |

前移的节点原本就持有这部分数据，只是换了一个位置；真正缺数据的，只有补到列表末尾的那一个节点。（计划内缩容时，前移节点经验证的准入可以直接带入新拓扑；故障时则需在后台重新验证，见第 6 节。）

## 3. 为什么“并入”不需要搬数据

每个数据节点只有一张内存记录表（`records`），自己作为 owner 负责的键和作为 follower 复制来的键存在同一张表里，并不按角色分开存放。节点是 owner 还是 follower，完全由它当前安装的拓扑决定。

因此，B 从“A 的区间的第一个 follower”变成“合并区间的 owner”，不需要复制、导入或转换任何数据。新拓扑一装上，B 就开始用它早已持有的记录为这些键服务。这就是“follower 的数据并入下一个 owner 的管辖范围”的含义：变化的只是拓扑中的归属关系，数据原地不动。

对比扩容：新节点加入时，它在所有相关区间中都不持有数据，必须经过快照复制、增量回放、短暂停写和校验。缩容和故障接管则把这一步省掉了，或者推迟到后台去做。

## 4. 前提：必须证明新 owner 的数据是完整的

“第一个 follower 持有数据”只是结构上的预期，实际不一定成立。例如：

- follower 刚加入集群，初始快照还没复制完；
- follower 与 owner 之间的连接断过，复制流有缺口；
- 区间合并后，新 owner 只覆盖了其中一部分子区间。

所以系统把“应该在哪里”和“确实准备好了”分开记录。Coordinator 为每个 follower 持久化一条**准入（admission）记录**，绑定拓扑 epoch、精确的区间边界、节点和进程实例，只有在快照和连续的增量历史都经过验证后才写入。

接管时，Coordinator 会检查合并后区间的**每一个组成部分**：新 owner 要么原本就是这部分的 owner，要么是这部分的第一个 follower，**并且**持有这部分的准入记录。任何一部分不满足，都不会发布新拓扑，**不完整的副本永远不会被提升**。

## 5. 计划内缩容

当目标拓扑只是删除节点、不同时修改其他配置时，Coordinator 走这条“自然继承”（代码中称为 direct merge）路径：

1. **检查结构条件。** 确认每个合并区间的新 owner 都是各组成部分的原 owner 或第一个 follower，且当前写入策略要求的 follower 在结构上都已持有数据。
2. **补齐缺失的准入（如有）。** 若某个必需的 follower 还没有准入记录，先在后台完成补种。这一步在停写之前进行，不影响服务。
3. **短暂暂停写入。** 读请求照常进行。
4. **等待复制流追平。** 对每一对“旧 owner → 新 owner”以及策略要求的 follower，等待 follower 已应用的序号追上 owner 已发出的序号。离开的节点仍在线，所以它最后的写入可以全部发出去。
5. **再次验证。** 确认覆盖关系和租约在停写期间没有变化。
6. **发布新 epoch。** 已追平的 follower 的准入记录直接带入新拓扑。
7. **激活、清理与停止。** 各节点安装新拓扑后恢复写入；不再需要的副本被删除，最后才停止离开的节点。
8. **后台补齐副本数。** 列表末尾新补上的节点通过快照加增量获得数据。

在仓库记录的 20 次连续测试中（9 ↔ 10 个节点，RF=3，`FirstSuccessor`，20,000 个键，迁移期间持续写入），需要复制数据的扩容耗时中位数为 7.958 秒，而缩容为 0.595 秒（最小 0.568 秒，最大 0.616 秒）。这是本地、小规模的测量，只说明两种路径的量级差别，不代表百万键规模下的迁移性能。

## 6. 故障接管

故障时离开的节点已经无法配合，流程有三点不同：

1. **确认故障。** 节点的租约已过期即可确认；否则需要至少两个独立节点持续报告它不可达。只有一对节点之间互相连不通时，系统不会贸然驱逐任何一方。
2. **隔离旧 owner。** Coordinator 停止为它续约，并**等到它的租约一定已经过期**。租约过期的节点会自行停止服务，所以此后不可能有两个 owner 同时接受写入。
3. **证明覆盖。** 与缩容相同，新 owner 必须对每个组成部分持有准入记录。
4. **发布新 epoch。** 无法再“追平”故障节点，所以没有停写和等待追平这两步。
5. **读先恢复，写按策略恢复。** 新拓扑安装、租约生效后读即恢复；写何时恢复取决于写入策略（见下表）。
6. **后台修复。** 准入记录绑定拓扑 epoch 和复制流，当前实现在故障路径下不把任何旧准入带入新拓扑，所以新拓扑中的 follower（包括前移的节点，以及未受故障影响的区间的 follower）都要通过后台修复，以快照加增量重新复制并验证后才能重新准入。服务恢复只依赖新 owner 已持有的数据，读取不等待这些修复；但 `FirstSuccessor` 和 `AllReplicas` 下的写入要等所需的 follower 重新准入。

| 写入策略 | 故障时会不会丢已确认的写入 | 接管后写入何时恢复 |
| --- | --- | --- |
| `OwnerOnly`（默认） | 可能：旧 owner 已确认但尚未复制出去的尾部写入会丢失 | 满足最低副本要求后立即恢复 |
| `FirstSuccessor` | 从健康状态出发，单节点故障不丢：每次确认前，下一任 owner 已经应用了这次写入 | 新的第一个 follower 追平并准入之后 |
| `AllReplicas` | 不丢 | 全部期望副本就绪之后 |

`FirstSuccessor` 的设计正是建立在第 2 节的观察之上：既然接管者是确定的，只要让它在确认前先收到写入，就能保证故障后已确认的写入不丢失。要求“任意两个副本确认”则做不到这一点：如果确认的是第二个 follower，而接管的是第一个 follower，这次写入仍会丢。

## 7. 与工业系统的对比

| | Redis Cluster | Cassandra / ScyllaDB | hashring-rs |
| --- | --- | --- | --- |
| 谁接管 | replica 发起选举，获得多数 master 投票者胜出 | 无固定 owner，剩余副本够数即可继续服务 | 由环的结构确定：第一个 follower |
| 如何确定接管者数据足够新 | 按复制偏移量尽力选最新的 replica，不保证 | 依赖 consistency level 与后续 repair | 准入记录证明数据完整，否则不提升 |
| 计划内缩容 | 需要先把 slot 迁走 | streaming 后执行 cleanup | 数据已在继承者手中，只需短暂停写、追平并发布 |
| 冗余恢复 | 需要手动或自动补 replica | 依赖 repair | 后台修复，与服务恢复分开 |

## 8. 局限

- **RF=1 时没有 follower**，节点故障后该节点的区间无数据可接管。
- **连续故障**：如果第一个 follower 在后台修复完成前也发生故障，新 owner 可能没有准入记录，这些区间会变为不可用，而不是返回不完整的数据。
- **负载分散依赖虚拟节点**：每个物理节点有很多 token，所以一个节点离开后，它的区间会分散到多个不同的继承者，而不是全部压到一个邻居身上。token 数量太少时，负载会集中在少数节点上。
- **扩容没有这个捷径**：新节点加入时总需要复制数据。
- **故障后的修复范围偏大**：当前实现在故障后重新准入所有 follower，而不只是受影响区间的 follower。计划内缩容已经会把追平的准入带入新拓扑；故障路径若能对未受影响、复制流仍连续的 follower 做类似的沿用，可以减少后台复制量，缩短 `FirstSuccessor` 下写入恢复的时间。这是一个待评估的优化方向。
- **Coordinator 自身不做高可用**：它不可用时无法执行接管，节点租约过期后会停止服务。
