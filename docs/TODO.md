## 中文

主测试配置采用当前默认值：RF=3、`OwnerOnly`、`minimum_admitted_copies=1`、`minimum_healthy_followers=0`。每个范围期望有两个异步跟随副本，但 `OwnerOnly` 写入不等待跟随副本 ACK。保持默认 30 秒逻辑操作期限；延长期限的运行只能作为单独的诊断结果。

干净源码版本 `89d23fa` 已完成九次 100 万键性能运行：`OwnerOnly`、`FirstSuccessor`、`AllReplicas` 各三次，其余工作负载配置一致；另有二十次 2 万键 `FirstSuccessor` 迁移运行全部完成。配置、结果与局限已记录在 Git 跟踪的[重复测量说明](optimizations/replica-ack-performance.md#repeated-measurements-on-committed-source)中；原始 `results/` 未纳入 Git，不假定队员拥有这些文件。因此下面的工作重点是负载形态、故障期间的行为和未覆盖的规模，不重复刷相同配置的基线。性能比较在相同机器条件下至少重复三次，保留每次的原始结果；失败运行也保留已完成阶段和错误证据。

1. [ ] **稳态容量、延迟与操作期限。** 扩展实验 crate 的工作负载，在 10 节点、RF=3、`OwnerOnly` 下分别测试并发度 1/16/64/128、128 B/4 KiB 值，以及持续的 PUT、GET、PUT/GET/DELETE 混合负载。先根据[已记录的 100 万键策略比较](optimizations/replica-ack-performance.md#one-million-key-write-policy-comparison)分析 `OwnerOnly` 写入速率波动；若现有文档不足以定位原因，补充带诊断采样的运行，再决定是否需要更多相同配置的重复运行。记录负载进行时的吞吐量和 p50/p95/p99 延迟、按原因分类的重试与期限结果、各节点 CPU/RSS、跟随副本延迟；逐阶段核验写入、读取和删除结果。不要用批量写入结束后的少量串行 PUT 延迟代表负载中的尾延迟。

2. [ ] **复制积压与恢复。** 优先做可控的跟随副本减速或短时断链实验：在持续写入后停止负载，按时间采样每条流的队列深度、容量拒绝、复制延迟、内存和恢复耗时。核验容量耗尽时在应用变更前返回可重试错误、积压保持有界、链路恢复后按序追平且数据正确。先手工注入故障；只有注入机制可复用时才加入实验 crate。RF=1 与 RF=3 的匹配基线仅在需要量化复制开销时执行，不扩展成完整配置矩阵。

3. [ ] **持续流量下的成员迁移。** 以默认 `OwnerOnly` 运行 9→10→9 节点迁移，从 10 万键和持续混合操作开始；稳定后再提高到 100 万键。覆盖快照复制、切换和 RF 修复，并在每个阶段核验成功写入的最终值与成功删除的缺失状态。记录迁移阶段耗时、原始节点 RPC 的临时阻塞、客户端重试原因、操作期限与恢复到完整 RF 的时间。[已记录的 2 万键 `FirstSuccessor` 重复运行](optimizations/replica-ack-performance.md#firstsuccessor-20k-scale-out-reliability)不能替代这个场景。

4. [ ] **负载中的跟随副本丢失。** 使用至少四个初始节点，预先选定“所有者存活、故障节点是跟随副本”的键，再杀死该跟随节点；持续执行默认 `OwnerOnly` 写入和读取。核验这些范围不因副本数量下降而被 ACK/可用性门槛错误拒绝，且 RF 下降有状态可查。`OwnerOnly` 仍可能因复制队列或节点共享内存预算耗尽而背压；单独统计容量背压、影响范围和恢复时间，不要求故障期间零阻塞。在替换节点加入后完成修复与数据核验。现有 availability 模式固定为三个初始节点加一个替换节点；此场景需要新实验分支或手工集群。

5. [ ] **负载中的所有者丢失。** 在故障前、故障中和修复后持续执行混合操作，换多个 hash seed 与故障所有者；记录每个请求的 ID、键、操作及值、调用与完成时间、结果、返回版本（若有）和拓扑 epoch，并保存故障前可获取的副本复制进度，以便恢复后核对不确定写入。测量受影响范围的不可用区间、发布新拓扑、读写恢复、新所有者分布及 RF 修复。将 `OwnerOnly` 故障切换后可由已记录历史和副本进度解释的已 ACK 变更回退单独统计，包括旧值重新出现、已 ACK 的删除丢失；不要把“近期”当作固定时间窗口，也不要把任意旧值都算作允许回退。证据不足的结果单列为无法判定，不计作通过；历史中不可能出现的值、旧所有者在被隔离或租约失效后仍接受新写入、或无法恢复，均判为失败。

6. [ ] **协调器重启与连续节点更替。** 在上述单次故障实验稳定后，先增加一次“带负载且正在修复”的协调器重启，核验租约自我隔离、拓扑恢复以及没有冲突所有者。随后运行 30–60 分钟的连续更替：每次只让一个节点故障，等上一次修复完成后再进行下一次。逐轮记录不可用时间、RF 恢复、重试与 CPU/RSS/复制延迟漂移。协调器高可用不在当前契约内，因此不要把重启期间完全无中断作为通过条件。

7. [ ] **响应丢失后的端到端重试。** 增加小规模真实进程测试：在 PUT/DELETE 已应用后丢弃响应，随后完成成员迁移或所有者提升，在默认 60 秒去重窗口内使用相同 mutation ID 和请求内容重试。核验返回原结果与版本、没有重复应用，并保留从客户端逻辑请求到每次 RPC 的实际 mutation ID、拓扑 epoch 和结果关联。用后续同键变更检查旧请求重试不会覆盖新值或再次删除新值。迁移场景使用默认 `OwnerOnly`；提升场景使用 `FirstSuccessor`，并确认 mutation 及 receipt 已应用到将被提升的副本后再注入 owner 故障，以隔离去重验证与允许的异步尾部丢失。现有去重及 receipt 迁移单测不能替代客户端、响应丢失与跨所有者恢复的联动验证。

8. [ ] **同键并发操作的历史正确性。** 增加小规模、多个客户端针对同一组键并发 PUT/GET/DELETE 的测试，记录调用和完成时间、参数、返回值、版本及拓扑 epoch。先在单一所有者 epoch 内检查历史是否存在符合实时先后关系的合法串行执行，再覆盖无节点故障的成员迁移交接。检查中途读取和删除语义，而不只核验最终状态。对 `MayHaveApplied` 保留可能已生效的分支，不能把超时直接视为未执行；OwnerOnly 故障切换另按允许回退的契约核验，不套用跨 failover 的严格线性一致性要求。

建议执行顺序：先补齐负载中的延迟、重试和请求结果记录，完成 7、8 的小规模正确性验证；再做 4、5、3；随后做 2；最后做 6 的长时间运行。每次运行使用独立结果目录，并保存实际配置、源码与二进制标识、事件日志、进程日志、拓扑/副本状态及失败时的部分结果。后续在本清单中引用已完成实验前，先将配置、源码版本、关键结果和局限记录到 Git 跟踪的文档，并链接该文档；仅存在于本地 `results/` 的运行不作为共享基线。

## English

Use the current defaults for the main profile: RF=3, `OwnerOnly`, `minimum_admitted_copies=1`, and `minimum_healthy_followers=0`. Each range desires two asynchronous followers, but an `OwnerOnly` write waits for neither follower's ACK. Keep the default 30-second logical operation deadline; runs with a longer deadline are separate diagnostics.

On clean source revision `89d23fa`, all nine one-million-key performance runs completed: three each for `OwnerOnly`, `FirstSuccessor`, and `AllReplicas`, with the remaining workload configuration held constant. All twenty 20k-key `FirstSuccessor` migration runs also completed. Configuration, results, and limitations are recorded in the Git-tracked [repeated measurement notes](optimizations/replica-ack-performance.md#repeated-measurements-on-committed-source). Raw `results/` files are not tracked by Git; do not assume teammates have them. The work below targets different load shapes, behavior during faults, and larger migrations instead of repeating those same baselines. Repeat performance comparisons at least three times under comparable machine conditions and retain every raw run, including partial evidence from failures.

1. [ ] **Steady-state capacity, latency, and deadlines.** Extend the experiment crate workload to run sustained PUT, GET, and mixed PUT/GET/DELETE traffic on 10 nodes with RF=3 and `OwnerOnly`. Sweep concurrency 1/16/64/128 and 128 B/4 KiB values. First investigate OwnerOnly write-rate variation using the [documented one-million-key policy comparison](optimizations/replica-ack-performance.md#one-million-key-write-policy-comparison). If the documentation cannot identify the cause, add runs with diagnostic sampling before deciding whether more identical repeats are useful. Record throughput and p50/p95/p99 latency during load, retries by cause, deadline outcomes, per-node CPU/RSS, and follower lag; verify writes, reads, and deletes after each phase. Do not treat the few serial PUTs sampled after bulk loading as loaded tail latency.

2. [ ] **Replication backlog and recovery.** Prioritize a controlled slow-follower or short link-loss run: write continuously, stop the load, and sample each stream's queue depth, capacity rejections, replication lag, memory, and drain time. Verify retryable rejection before mutation application when capacity is exhausted, bounded backlog, ordered catch-up, and correct data after recovery. Inject the fault manually first; add it to the experiment crate only if the mechanism is reusable. Run one matched RF=1 versus RF=3 baseline only when quantifying replication overhead is needed.

3. [ ] **Membership migration under continuous traffic.** Run 9→10→9 nodes with default `OwnerOnly`, starting at 100k keys and continuous mixed operations; increase toward one million keys after the smaller run is stable. Cover snapshot copy, cutover, and RF repair. After each stage, verify final values for successful writes and absence for successful deletes. Record phase durations, temporary blocks seen through raw node RPCs, client retry causes, operation deadlines, and time to full RF. The [documented repeated 20k-key `FirstSuccessor` runs](optimizations/replica-ack-performance.md#firstsuccessor-20k-scale-out-reliability) do not cover this profile.

4. [ ] **Follower loss under load.** Start with at least four nodes and select keys whose owner stays alive while a follower node is killed. Continue default `OwnerOnly` writes and reads. Verify that reduced replica counts do not incorrectly reject writes through ACK or availability gates, and that the reduced RF is reported. `OwnerOnly` can still encounter backpressure when replication queues or the shared node memory budget are exhausted; record capacity backpressure, affected ranges, and recovery time separately instead of requiring uninterrupted writes throughout the fault. Verify repair and data correctness after a replacement joins. The current availability mode fixes the layout at three initial nodes plus one replacement, so use a new experiment scenario or a manual cluster.

5. [ ] **Owner loss under load.** Run mixed traffic before, during, and after failure, varying the hash seed and failed owner. Retain a request ledger with ID, key, operation and value, invocation and completion times, result, returned version (if any), and topology epoch; save available pre-failure replica progress to reconcile uncertain writes after recovery. Measure affected-range unavailability, topology publication, read/write recovery, new-owner distribution, and RF repair. Count acknowledged changes rolled back under `OwnerOnly` separately when the recorded history and replica progress can explain them, including an older value reappearing or an acknowledged delete being lost. Do not treat “recent” as a fixed time window or classify every old value as a permitted rollback. Report outcomes with insufficient evidence as inconclusive, not as passes. Values impossible under the recorded history, new writes accepted by the old owner after fencing or lease expiry, and failure to recover remain failures.

6. [ ] **Coordinator restart and sequential churn.** Once the single-fault scenarios are stable, restart the coordinator once during loaded repair and verify lease self-fencing, topology recovery, and absence of conflicting owners. Then run 30–60 minutes of sequential node failures and replacements, waiting for each repair to finish before the next fault. Record per-cycle unavailability, RF recovery, retries, and drift in CPU/RSS and replication lag. Coordinator HA is outside the current contract, so uninterrupted service throughout a coordinator restart is not a pass condition.

7. [ ] **End-to-end retries after response loss.** Add small real-process tests that drop a response after a PUT/DELETE has applied, then complete membership migration or owner promotion and retry the same mutation ID and payload within the default 60-second receipt retention period. Verify the original result and version, no duplicate application, and a trace linking each client logical request to the actual mutation ID, topology epoch, and outcome of every RPC attempt. Use a subsequent mutation of the same key to verify that retrying the old request neither overwrites nor deletes the newer value. Use default `OwnerOnly` for migration. For promotion, use `FirstSuccessor` and confirm that both mutation and receipt have reached the replica to be promoted before injecting owner failure, separating deduplication verification from permitted asynchronous tail loss. Existing deduplication and receipt-migration unit tests do not replace this combined client, response-loss, and cross-owner recovery check.

8. [ ] **Concurrent same-key history correctness.** Add small tests with multiple clients issuing concurrent PUT/GET/DELETE operations against the same set of keys. Record invocation and completion times, arguments, returned values, versions, and topology epochs. First check that histories within one owner epoch admit a legal serial execution respecting real-time ordering, then cover membership handoff without node failure. Check intermediate reads and delete semantics, not only final state. Retain the possibility of application for `MayHaveApplied` operations rather than treating timeouts as non-execution. Validate OwnerOnly failover separately under its permitted rollback contract instead of requiring strict linearizability across failover.

Execution order: add in-load latency, retry, and request-outcome records first, and complete the small correctness checks in 7 and 8; run 4, 5, and 3 next; then run 2; leave the long run in 6 for last. Give each run a separate result directory and retain the effective configuration, source and binary identity, events, process logs, topology/replica status, and partial results on failure. Before citing a completed experiment in this checklist, record its configuration, source revision, key results, and limitations in a Git-tracked document and link that document; runs available only in local `results/` are not shared baselines.
